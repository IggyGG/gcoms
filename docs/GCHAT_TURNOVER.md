# Actual GChat turnover journey

`scripts/gchat-turnover.py` runs the built GChat daemon and owner IPC probe with
four real GComs queue relays in disconnected network namespaces. It uses the
unchanged profile-22 transport, hourly credential epochs and 1800-second carrier
limit. It makes no fleet/provider/production connections and does not select a
production profile.

Build the exact paired sources with `scripts/build-fleet-files.py` in a managed
reservation, then run the controller as the ordinary workstation user:

```sh
WORKSTATION_BUILD_BUDGET=17179869184 workstation-batch -- \
  workstation-builds run --budget 17179869184 --wait 30 --timeout 18000 \
  --output "$PWD/target/gchat-turnover" -- \
  python3 scripts/gchat-turnover.py \
  --build target/gchat-turnover/build --out target/gchat-turnover/run-01 --expiries 3
```

Use a fresh output directory. The controller validates all three immutable
executables against `build.json`, retains source/build/tool hashes, and refuses
root invocation. Its privileged child enters separate network, mount and PID
namespaces before any relay/application launch. Only connected fixture subnets
exist; no default route or external resolver is supplied. Children run as the
ordinary owner. Cleanup records child exits, retired-namespace membership and
unchanged host interfaces.

The journey performs actual invitation/join, authenticated chat and returned
acknowledgment, 64 KiB import/accept/independent export, and same-identity receiver
reopen/re-export. It then accepts chat with the receiver stopped, restarts both
clients, and requires one received copy and a returned acknowledgment without
resubmission. Reopen uses the retained profile/directory; it neither recreates the
profile nor replays the original potentially expired bootstrap bundle.

For each real hourly expiry it imports a unique 256 MiB file, requires the
transfer to remain incomplete immediately before expiry, and checks fresh
verified bytes plus both Interactive/Bulk contact/channel subscriptions within
300 seconds. A concurrent chat must receive its returned acknowledgment. The
file must then independently export with the expected hash and survive receiver
reopen. Distinct generated bytes per generation prevent prior cached content
from substituting for transfer progress. Files completing before the boundary
fail this scenario rather than being reported as turnover coverage.

Setup has one 300-second deadline, including invitation/join IPC. Recovery keeps
its own 300-second limit. A timeout retains an unobserved operation outcome; it
does not prove cancellation. Daemon restart removes only a stopped controller's
private probe socket, never a live process's socket or a profile file.

This is a focused application reliability gate, not fleet latency/soak or privacy
qualification. The header-only SYN/FIN/RST capture supports connection-lifecycle
analysis but is not an all-egress privacy capture. A long run alone does not prove
that a particular connection ended because of the carrier cap while credentials
were fresh; retain that causal/lifecycle evidence separately. Explicit fixture
bootstrap does not qualify installed signed-network/provider onboarding.

For a separate real carrier-limit journey, `GCOMS_GC2_LIFECYCLE=1` opts each
process into local `gc2_entry_lifecycle` stderr records. They include a
process-local sequence, client/server-channel role, wall timestamp, monotonic
elapsed time, original credential expiry, the already computed deadline and
the unchanged 1800-second maximum. Client class-mux readiness and deadline,
transport-end or future-drop completion are separate events. No address,
service identity, capability, message body or unbounded error string is logged.
Logging is disabled by default and does not wake the owner or replace a deadline.
Bind its use in the workload manifest. A `dropped` or `transport_ended` event is
not itself evidence that a lifetime deadline expired. To qualify the carrier
limit, retain a deadline event near 1800 elapsed seconds with original authority
still fresh, application work crossing it, and authenticated recovery receipts.

## Fair retry prerequisite

GComs `fbab1959e4380a32f3b30d76c682b4d18985e4f1`, paired with GChat
`d9e9e1d3a538bfb77b92a2f710f0c253c838b51c`, passed 303 node library tests
(one existing exclusion), 160 GChat workspace tests (one separate namespace
exclusion), and both strict all-feature/all-target Clippy checks on unchanged
snapshots. `target/channel-fairness-01/summary.json` binds the logs and original
cross-channel and recipient-lane saturation failures; its SHA-256 is
`f62411e4eef9c0e11a9ee71a2034e5521c7ecf46d9cc74ba190646d13dea673d`.

The data retry loop retains bounded plans/receipts between ticks, rotates channel
admission, and advances fragments independently per recipient. Full/Pending
keeps the same unadmitted fragment; another usable lane can progress. Total
recipient accounting prevents partial forwarding from becoming full completion.
Scheduler-owned in-flight work retains its accounting until it actually ends.
Hop receipts do not acknowledge message delivery. Control/subscription/cover
clocks, hop deadlines and authority lifetimes remain unchanged. These checks
are not the whole-repository native/package or application turnover result.

The first actual-daemon attempt retained a 30-second controller IPC timeout
during remote join. The second independently exported the small file, then the
restarted probe failed on its stale socket while GChat itself reopened. Both
failed reports and complete cleanup remain under `target/gchat-turnover-01/`;
neither is a turnover pass. Controller regressions cover these two failures.
